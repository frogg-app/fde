FDE — memory & CPU investigation

Static analysis of talented-unicorn @ 6c0fb3c · 2026-09-05 · scope: Android (Expo) and Windows (Tauri) slowness

Method and its limits. This is a source-level audit — I read the streaming, rendering, transport and store code paths and traced allocation and retention by hand. I did not attach a profiler to a running Android or Windows build, so the ranking below is my judgement about likely impact, not measured data. Every finding is a concrete, verifiable code defect with file and line references; the "expected impact" column is an estimate. The last section lists the measurements I'd take to confirm the ordering before anyone spends a sprint on it.

Summary

Two genuinely distinct problems are stacked on top of each other, which is why both platforms feel bad in different ways:

  • Shared (hits Android and Windows equally): the assistant-message render path re-parses markdown and re-tokenizes syntax highlighting from scratch on every animation frame while a turn is streaming. This is quadratic in message length and is almost certainly the dominant CPU cost during an active agent turn.
  • Windows-only: every inbound daemon WebSocket frame crosses the Tauri IPC boundary as its own emit, with binary frames base64-encoded. Android's app speaks WebSocket directly and pays none of this.
  • Memory: one unambiguous unbounded retention bug in @fde/client that holds whole file bodies forever, plus a syntax-highlight cache bounded by entry count rather than bytes that the streaming path actively poisons.

Findings

1. Full markdown parse on every animation frame while streaming Critical

CPU · Android + Windows · apps/ui/src/components/message.tsx:1950, apps/ui/src/utils/split-markdown-blocks.ts

AssistantMessage splits its text into markdown blocks for rendering:

// message.tsx:1950
const blocks = useMemo(() => splitMarkdownBlocks(revealedMessage), [revealedMessage]);

The memo looks like it protects the call, but revealedMessage comes from useRevealedText (apps/ui/src/hooks/use-revealed-text.ts), which is a requestAnimationFrame loop: while phase === "streaming" it advances the revealed prefix and calls forceRender on every frame. So the memo's dependency changes ~60 times a second, and the memo never hits.

What runs 60 times a second is not cheap. splitMarkdownBlocks runs a complete markdown-it block parse of the entire text purely to decide which blank lines are structural: 

// split-markdown-blocks.ts
function getStructuralBlankLines(text: string, lines: string[]): Set<number> {
  const blankLines = new Set<number>();
  for (const token of markdownBlockParser.parse(text, {})) {  // <-- full parse
    ...

Why it compounds

Cost is O(text length) per frame and the text grows monotonically through the turn, so total work across a turn is O(n²). Block promotion in the reducer caps n at one markdown block rather than the whole message, which helps — but a single long code fence, a long table, or a long unbroken paragraph never gets promoted, so n is the whole fence. A 500-line code block streamed in over 30 seconds means roughly 1,800 full parses of a document that averages 250 lines.

This is my primary suspect for the shared slowness. It is the only thing I found that scales with both message length and frame rate simultaneously, on both platforms.

The same call is also in the reducer

// apps/ui/src/types/stream.ts:1777, inside promoteCompletedAssistantBlocks
const blocks = splitMarkdownBlocks(activeItem.text);

The reducer queue flushes on a frame boundary too — scheduleAgentStreamReducerFlush races a requestAnimationFrame against a setTimeout(48ms) (session-stream-reducers.ts:1881) — and flushes all pending agents at once. So with several agents streaming, this is one full parse per agent per frame, on top of the per-message render cost above.

Fix

  1. Decouple block splitting from the reveal clock. Split on the underlying renderedMessage.text, not on revealedMessage, and apply the reveal prefix only to the final block. Text arriving from the daemon changes far less often than 60 Hz, so the memo would start hitting. This alone should remove most of the cost.
  2. Make splitMarkdownBlocks incremental. It is called repeatedly with strings that are prefixes of one another. Cache the structural-blank-line scan keyed by a prefix length and only re-parse the tail after the last confirmed block boundary.
  3. Failing both, memoize splitMarkdownBlocks behind a small LRU keyed by text — a band-aid, but a one-line one.

2. Streaming code fences re-tokenize every frame and poison the highlight cache Critical

CPU + memory · Android + Windows · apps/ui/src/utils/highlight-cache.ts, apps/ui/src/components/highlighted-code-block.tsx:77

Two separate defects that reinforce each other, both triggered by the same thing: a code fence being streamed in.

2a — CPU: the tokenization cache cannot hit during streaming

// highlight-cache.ts:50
export function tokenizeToLines(code: string, ext: string | null) {
  ...
  const cacheKey = `${ext}:${code}`;        // key is the ENTIRE source text
  const cached = tokenizationCache.get(cacheKey);

The cache key is the full source. While a fence streams, every frame presents a different, longer string, so every lookup misses and the whole grown block is re-tokenized from scratch. HighlightedCodeBlock has no streaming gate at all: 

// highlighted-code-block.tsx:77
const keyedLines = useMemo<KeyedLine[] | null>(
  () => highlightToKeyedLines(renderedCode, fenceLanguageToExtension(language)),
  [renderedCode, language],   // renderedCode changes every frame
);

Note there is no phase prop on this component — it cannot tell streaming from complete. On top of the tokenizer, highlightToKeyedLines is not cached and allocates one wrapper object per token per line on every call, then renderCodeSegments allocates a React element per token. For a 500-line block that is tens of thousands of objects per frame, straight into the nursery. On Android's JS engine this is exactly the shape that produces visible GC stutter.

2b — Memory: an LRU bounded by count, fed one entry per prefix

const tokenizationCache = new LRUCache<string, HighlightToken[][]>(200);

200 entries, with no byte budget, while MAX_HIGHLIGHT_CHARS admits inputs up to 100,000 characters. Worst case the keys alone are 20 MB, and the values — nested arrays of token objects — are typically several times the size of the source they came from. A few hundred MB is reachable.

Streaming makes this concrete rather than theoretical. Every frame inserts a new entry for the current prefix. A 50 KB fence streamed over 400 frames writes 400 entries averaging 25 KB of key each — and evicts all 200 genuinely useful entries in the process. So the cache both bloats and stops working, at the same moment.

Fix

  1. Gate highlighting on phase. Thread the existing MarkdownPhase down to HighlightedCodeBlock and render plain monospace text while phase === "streaming", highlighting once on completion. Cheapest fix, largest win, and visually near-identical.
  2. Don't cache streaming prefixes. Give tokenizeToLines a { cache: boolean } option and pass false for in-flight text.
  3. Budget the LRU in bytes, not entries — e.g. 8 MB of accumulated code.length — and hash the key rather than storing the full source as the key.
  4. Memoize highlightToKeyedLines alongside the token cache so the keyed-line and React element allocation isn't repeated on unrelated re-renders.

3. completedBinaryFileReads is never cleared on the failure path Low

Memory leak · Android + Windows · packages/client/src/daemon-client.ts:4380–4412, 5961–5970

The one finding here that is an outright bug rather than a design cost. Binary file reads are assembled from chunk frames and parked in a map for the awaiting caller to collect: 

// daemon-client.ts:5961 — chunk stream completes
const bytes = concatByteChunks(transfer.chunks, transfer.size);
this.activeBinaryFileTransfers.delete(frame.requestId);
this.completedBinaryFileReads.set(frame.requestId, { bytes, ... });   // full file body
// daemon-client.ts:4388 — the caller
try {
  const payload = await this.requestFileExplorer(cwd, path, "file", id, true, maxBytes);
  if (payload.error) throw new Error(payload.error);
  const binaryResult = this.completedBinaryFileReads.get(id);
  if (binaryResult) {
    this.completedBinaryFileReads.delete(id);   // only cleared here, on success
    return binaryResult;
  }
  ...
} finally {
  this.pendingBinaryFileReads.delete(id);
  this.activeBinaryFileTransfers.delete(id);
  // completedBinaryFileReads is NOT cleared
}

The finally block cleans up two of the three maps and forgets the third — the only one holding megabytes.

How it triggers — narrower than it first looks

Correction to my initial read. I first assessed this as leaking on any RPC timeout, which would have made it the dominant Android leak. Tracing it properly while fixing it, that is wrong: the finally clears activeBinaryFileTransfers, and the completion handler at 5927 bails when there is no active transfer — so a late frame arriving after a timeout never reaches the set. The insert and the awaiting get are also separated only by a microtask, which a timer cannot preempt.

The surviving path is narrow: the daemon returns a payload.error for a request whose bytes already landed, so readFile throws at 4397 before reaching the get/ delete at 4400. That leaks one file body per occurrence, permanently.

So this is a real defect with a genuinely trivial fix, but Low severity in practice, not High — it is not the Android memory story I initially suggested. Findings 1 and 2 carry that weight instead.

Fix

Add this.completedBinaryFileReads.delete(resolvedRequestId) to the existing finally block. That covers the synchronous-rejection case. For the genuinely late frame — completion arriving after the caller is gone — also refuse to insert when there is no corresponding pendingBinaryFileReads entry, and add a TTL sweep as a backstop. All three are small, independent changes.

4. One Tauri emit per WebSocket frame, binary base64-encoded High

CPU · Windows (and macOS/Linux desktop) · apps/desktop/src-tauri/src/transport/task.rs:145–162, transport/session.rs:202–208, commands/mod.rs:38

This is the clearest reason Windows would feel worse than Android on the same workload — Android's Expo app opens a WebSocket directly and never touches this code.

The transport read loop forwards each frame individually:

// transport/task.rs
Some(Ok(message)) => {
    if let Some(event) = incoming_message_event(&self.id, &message) {
        if self.is_current() { (self.emit)(event); }   // one emit per frame
    }
}
// commands/mod.rs:38
let emit: EventSink = Arc::new(move |payload| {
    if let Err(error) = handle.emit(TRANSPORT_EVENT, payload) { ... }
});

There is no batching or coalescing. During an agent turn the daemon emits many small deltas per second, and each one is a full IPC round trip: build a serde_json::Value, serialize it, post it to WebView2, parse it in JS, dispatch to listeners. WebView2's IPC has meaningful per-message overhead, so the fixed cost per frame dominates the payload cost for small deltas.

The binary path is worse

// transport/session.rs:206
pub fn binary_message_event(session_id: &str, bytes: &[u8]) -> Value {
    json!({ "sessionId": session_id, "kind": "message", "binaryBase64": BASE64.encode(bytes) })
}

Binary frames — which is how file reads are chunked — get base64'd (+33%), embedded in a JSON value, serialized again by Tauri's IPC with escaping, parsed in JS, then base64-decoded back to bytes in decodeBase64ToBytes. That's roughly four full copies of every byte, all on or adjacent to the UI thread. Opening a 10 MB file means moving ~40 MB through the main thread.

Fix

  1. Coalesce text frames. Buffer inbound frames in the Rust task and emit an array on a short interval (4–8 ms) or when the buffer hits a size threshold. The JS side already handles messages one at a time; the change is a loop. This trades a few ms of latency for a large constant-factor reduction in IPC crossings.
  2. Get binary off the JSON channel. Tauri v2 supports raw byte responses via a custom protocol / tauri::ipc::Response. Serving file bodies over that instead of base64-in-JSON removes three of the four copies.
  3. Use emit_to, not emit — see finding 5.

5. The global transport event fans out to every session listener Medium

CPU · Windows · apps/ui/src/desktop/daemon/desktop-daemon.ts:220–233, desktop-daemon-transport.ts:177–204

Every transport instance subscribes to the same global local-daemon-transport-event, and the per-session filter happens last: 

// desktop-daemon.ts:220 — runs for EVERY listener, on EVERY message
return listenToDesktopEvent<unknown>("local-daemon-transport-event", (payload) => {
  if (!isRecord(payload)) return;

    sessionId: toStringOrNull(payload.sessionId) ?? "",
    kind: ...,
    text: toStringOrNull(payload.text),
    binaryBase64: toStringOrNull(payload.binaryBase64),   // whole base64 blob, coerced
    ... 8 fields total
  });
});
// desktop-daemon-transport.ts:178 — the filter, AFTER the object is already built
const handleEvent = (payload: LocalDaemonTransportEvent) => {
  if (disposed || payload.sessionId !== sessionId) return;   // discard

With M connected daemons, each message allocates and populates M normalization objects and discards M−1 of them. Combined with finding 4's lack of batching, that is M × frames-per-second wasted allocations. It is a constant factor rather than an algorithmic problem, which is why I've rated it Medium — but it is essentially free to fix.

Fix

Filter on sessionId before constructing the normalized object. Better: emit per-session event names (local-daemon-transport-event:{sessionId}) from Rust and use emit_to so the routing happens once, in Rust, instead of once per listener in JS.

6. Store identity churn re-runs every selector on every flush Medium

CPU · Android + Windows · apps/ui/src/stores/session-store.ts:1045–1056

setAgentStreamState is careful about change detection — it bails early when nothing changed — but when something did change it replaces the identity of the entire tree: 

return {
  ...prev,
  sessions: { ...prev.sessions, [serverId]: { ...session, agentStreamTail: nextTail, ... } },
};

Any selector reading state.sessions therefore re-runs on every stream flush — which is frame-rate, ~60 Hz, and flushes all agents together. There are 172 store subscription sites in apps/ui. Each re-runs its selector function and its equality check per flush, even for components displaying data that provably did not change (the sidebar, the tab strip, settings panels).

To be fair to the existing code, the hot selectors are already defensively written — use-aggregated-agents.ts preserves object identity field-by-field so downstream memo comparisons bail, and legacy-migration.tsx returns a joined string rather than an array. This is a well-tuned system fighting its own store shape. But the selector bodies themselves still run 60 times a second, and several allocate a fresh object before comparing (use-aggregated-agents.ts:42–50 builds a new Record per call for useShallow to discard).

Fix

The structural fix is to move the per-agent stream tails out of the single sessions record into their own store — or a per-agent external store subscribed via useSyncExternalStore — so that a stream delta only notifies subscribers of that agent. That's real work. A cheaper interim step: audit the selectors that fire on state.sessions and narrow them to the specific sub-map they read, so shallow comparison rejects earlier and allocates less.

7. A MarkdownIt instance per mounted assistant message Medium

Memory · Android + Windows · apps/ui/src/components/message.tsx:1503 

const markdownParser = useMemo(createAssistantMarkdownParser, []);

The empty dependency array makes this per-component-instance, not per-app. Every mounted assistant message constructs and retains its own MarkdownIt — full rule chains, options objects, the linkify machinery, and a patched validateLink closure.

Every other surface in the codebase gets this right with a module-level singleton:

src/utils/rich-clipboard.ts:3        const markdownRenderer = createAssistantMarkdownParser();
src/components/plan-card.tsx:13      const planMarkdownParser = createMarkdownParser({ linkify: false });
src/components/markdown/renderer.tsx:71 const defaultMarkdownParser = createMarkdownParser({ linkify: true });

message.tsx is the outlier — and it is the one on the hot path. With ~20 messages mounted (DEFAULT_MOUNTED_RECENT_STREAM_ITEMS) per agent panel, across several open agents, that is dozens of retained parsers. It also means construction cost on every mount, i.e. during fast scrolling, which is where Android scroll jank would show up.

Fix

Hoist to a module-level singleton like the other three call sites. The parser is stateless between render calls and the validateLink patch is constant, so there is no reason for per-instance construction. One-line change, and it makes the markdownRules memo below it (which lists markdownParser as a dependency) stable across instances too.

8. Unbounded Tauri transport channels — retracted

Withdrawn on closer reading · apps/desktop/src-tauri/src/transport/mod.rs:60, 162

I flagged mpsc::unbounded_channel() in the transport as an unbounded daemon → webview buffer. That was a pattern-match on the call, not a trace of the path, and it does not hold:

  • mod.rs:60 is the outgoing queue (app → daemon), and every message carries a oneshot reply that TransportManager::send awaits (mod.rs:105–110). Each caller blocks until its write completes, so depth is bounded by concurrent senders. That is backpressure, just expressed with a per-message ack.
  • mod.rs:162 is inside mod tests — a test-only sink.
  • The production inbound path never queues at all: emit calls handle.emit synchronously (commands/mod.rs:38).

No fix applied, and none needed. Recorded here rather than deleted so the claim isn't re-derived from the same grep later.

Suggested order of work

  1. Finding 1, step 1 — split blocks on the source text rather than the revealed prefix. Small, surgical, and if my reading is right it is the single largest win on both platforms.
  2. Finding 2, step 1 — thread phase into HighlightedCodeBlock and skip highlighting while streaming. Also small; removes the O(n²) tokenization and the cache poisoning together.
  3. Finding 3 — one line in a finally block. Do it regardless of profiling results; it is a straightforward bug.
  4. Finding 7 — one-line hoist to a module singleton.
  5. Finding 4 — batch inbound frames in the Rust transport task. Bigger change, and the main lever for Windows specifically.
  6. Findings 2b, 5, 8 — cache byte budget, pre-filter by session, bounded channels. Cheap hardening.
  7. Finding 6 — store restructuring. Only worth it if measurements show a floor remaining after the above.

How to confirm the ranking

The ordering above is inference from reading code. Before committing significant effort, I'd measure:

  • Windows: WebView2 DevTools performance profile during an active agent turn that includes a long code fence. Look for parse / tokenizeToLines / splitMarkdownBlocks self-time, and count __TAURI_EVENT_PLUGIN_INTERNALS__ callback invocations per second. If findings 1 and 2 are right, markdown-it should be the top self-time entry by a wide margin.
  • Android: Hermes sampling profiler over the same scenario, plus a heap snapshot before and after (a) streaming a long code block and (b) opening and cancelling several image previews on a throttled connection. Finding 3 predicts retained Uint8Arrays reachable from DaemonClient.completedBinaryFileReads; finding 2b predicts a large retained tokenizationCache dominated by key strings.
  • Both: the repo already has apps/ui/e2e/browser/agent-stream-smoothness.spec.ts and apps/ui/perf/side-pane-performance.spec.ts. Extending the smoothness spec with a long-code-fence fixture would turn findings 1 and 2 into a regression test rather than a one-off investigation.
  • Cheap sanity check for finding 1, no profiler needed: temporarily hard-code isTextRevealPacingSupported() to false (which makes useRevealedText return the text directly and stops the rAF loop) and see how much of the slowness disappears. If it largely does, finding 1 is confirmed and the fix is well-scoped.
