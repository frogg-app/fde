A plugin is a directory with a manifest (`fde-plugin.json`) and one entry point (`index.ts`). The
daemon compiles the entry point into two bundles:

- **Server bundle.** Runs in a Node subprocess on the daemon host. It registers RPC handlers.
- **Client bundle.** The daemon sends it to every connected app, which evaluates it. It registers
  UI: sidebar screens, workspace panels, Command Center items, slash commands, composer pills and
  attachment sources, timeline transformers and renderers, and themes.

Plugins are installed **per daemon**. Each host has its own plugin list, and a plugin only
appears in the app for the hosts that run it.

## Trust model

:::caution
Plugins are trusted, unsandboxed code. Server code, and Git `build` commands, run as the daemon
user on the daemon host, with full access to its files, processes, credentials and network.
Client code runs inside the FDE app. Dependencies and future updates of a Git source are part of
what you trust. Install only code you have read or whose author you trust.
:::

`fde plugin install` prints this warning on every install. There is no permission system,
signature check or sandbox.

## Enable plugins on a host

The global switch `pluginsEnabled` in `$FDE_HOME/config.json` defaults to `false`. While it is
off, configured plugins stay installed but report `disabled`.

In the app, open the host's **Settings → Plugins** and turn on **Enable plugins**. The page also
shows the trusted-code warning, installed plugins with **Reload**, **Enable**/**Disable**,
**Remove** and **Logs**, and an **Install directory** form.

<Screenshot src={appPluginsImg} alt="Host settings, Plugins section" />

From a shell on the daemon host, set the root key and reload:

```json title="~/.fde/config.json"
{
  "pluginsEnabled": true
}
```

```bash
fde reload
```

Turning the switch on starts every enabled plugin. Turning it off stops them all. Neither needs a
daemon restart. `fde reload --host <host>` reloads a remote daemon's own file; it does not edit it.

## Quickstart

<Steps>

1. Create a project. The directory must be empty or missing. The ID defaults to the directory
   name and must match `^[a-z][a-z0-9-]*$`.

   ```bash
   fde plugin init ~/plugins/hello-plugin
   ```

   This writes `fde-plugin.json`, `index.ts`, `main.client.tsx`, `package.json` and
   `tsconfig.json`. It does not install packages.

2. Read the generated entry point. It adds one surface and nothing else.

   ```ts title="index.ts"
   import type { PluginContext } from "@fde/plugin";
   import { MainSurface } from "./main.client";

   export default function contribute(plugin: PluginContext) {
     plugin.addSurface("main", MainSurface);
     return () => {};
   }
   ```

3. Make the surface reachable from the sidebar. The icon is a Lucide icon name.

   ```ts title="index.ts"
   plugin.addSurface("main", MainSurface);
   plugin.addSidebarItem({ id: "main", title: "Hello", icon: "Blocks", surface: "main" });
   ```

4. Install it on the local daemon. Use an absolute or `./`-relative path.

   ```bash
   fde plugin install ~/plugins/hello-plugin
   fde plugin ls
   ```

   `ls` should show `running`. **Hello** now appears in the sidebar for that host.

5. After each edit, reload the plugin.

   ```bash
   fde plugin reload hello-plugin
   ```

</Steps>

<Aside type="caution" title="Typechecking">
The generated `package.json` lists `@fde/plugin` as a dev dependency, but `@fde/plugin` is not
published to npm, so `npm install` fails outside the FDE repository. You do not need it to run a
plugin: the daemon compiles TypeScript itself and supplies `@fde/plugin`, `react`,
`react-native`, `@tanstack/react-query` and `zod` at runtime. To typecheck, create the project
inside an FDE checkout that has run `npm install`, so those modules resolve from the repository.
</Aside>

## Install and manage

### From a directory

```bash
fde plugin install /abs/path/to/plugin
fde plugin install ./plugin --id plugin-staging    # same code under a second ID
```

The runtime ID defaults to the manifest `id`. `--id` overrides it, so one directory can be
installed several times. The daemon records the path in `config.json` and compiles from it on
every start and reload. The app's **Install directory** form does the same; the path is on the
daemon host.

### From Git

```bash
fde plugin add owner/repository                         # GitHub shorthand
fde plugin add https://git.example.com/team/repo.git    # any Git URL, including ssh and scp-style
fde plugin add owner/monorepo:plugins/review            # plugin below the repository root
fde plugin add owner/repository --ref v1.2.0            # tag or commit: pinned
fde plugin add owner/repository --ref main              # branch: tracked
```

`add` and `install` are the same command. An existing directory always wins over a Git
interpretation. Without `--ref`, the remote's default branch is tracked. Git installs are only
available from the CLI.

The daemon clones into `$FDE_HOME/plugins/<id>/<commit12>-<uuid>/checkout`, initialises
submodules, runs the manifest's optional `build` commands, compiles, and only then activates the
plugin. Source metadata is kept in `$FDE_HOME/plugins/sources.json`.

```bash
fde plugin status             # fetch and compare installed vs latest commit
fde plugin update review      # update one Git plugin
fde plugin update --all       # update every Git plugin
```

A failed update discards the new checkout and keeps the running version.

### Lifecycle commands

| Command                  | Effect                                                                  |
| ------------------------ | ----------------------------------------------------------------------- |
| `fde plugin ls`          | Lists ID, status (`running`, `disabled`, `failed`), enabled, path, error |
| `fde plugin reload <id>` | Stops the plugin, recompiles from disk and starts it                     |
| `fde plugin disable <id>`| Stops it and sets `enabled: false`                                       |
| `fde plugin enable <id>` | Sets `enabled: true` and starts it if plugins are globally on            |
| `fde plugin remove <id>` | Stops it and removes its configuration                                   |
| `fde plugin logs <id>`   | Shows recent stdout and stderr from the plugin                           |

`remove` never deletes a directory you installed from. For a Git install it also deletes the
managed checkout under `$FDE_HOME/plugins/<id>`. Every management command accepts `--host` and
`--json`. See the [reference](/docs/plugins/reference/#cli) for every flag.

Source edits need `fde plugin reload`. Do not restart the daemon to pick up plugin changes;
restarting it also interrupts running agents.

## Client and server code

`index.ts` should only wire contributions. The compiler builds it twice and removes what does not
belong in each bundle:

- The server bundle keeps only `plugin.handle(...)`. All `plugin.add*(...)` calls, and imports of
  `*.client` modules from `index.ts`, are removed.
- The client bundle drops `plugin.handle(...)` and imports of `*.server` modules from `index.ts`.

Put runtime code in files named by where it runs:

| Suffix         | Runs in              | Holds                                                      |
| -------------- | -------------------- | ---------------------------------------------------------- |
| `*.client.tsx` | App                  | React components, hooks, styles, client callbacks          |
| `*.server.ts`  | Daemon subprocess    | Node APIs, files, processes, credentials, RPC handlers     |
| `*.shared.ts`  | Both                 | `defineRpc` contracts, Zod schemas, plain constants        |

Importing a `*.client` module into server code, or a `*.server` module into client code, fails
compilation unless the import is directly in `index.ts`. Top-level React Native calls such as
`StyleSheet.create` belong in `*.client.tsx`; in `index.ts` they would also run on the server.

The app provides `react`, `react-native`, `@tanstack/react-query`, `zod`, `@fde/plugin`,
`@fde/plugin/react-native` and `@fde/plugin/server` to client code. Other dependencies are bundled
from the plugin's `node_modules`. Node APIs are not available in the app.

## RPCs

Use an RPC when client code needs something only the daemon host can do, such as reading a file
or calling a vendor API with a secret. For normal FDE operations (workspaces, agents, providers,
config), call the FDE API directly with `useFde()` instead.

```ts title="greeting.shared.ts"
import { defineRpc } from "@fde/plugin/server";
import { z } from "zod";

export const greetRpc = defineRpc({
  name: "greeting.create",
  input: z.object({ name: z.string() }),
  output: z.object({ message: z.string() }),
});
```

```ts title="index.ts"
plugin.handle(greetRpc, async ({ name }) => ({ message: `Hello, ${name}` }));
```

```tsx title="greeting.client.tsx"
const greet = useRpc(greetRpc);
const { message } = await greet({ name: "Ada" });
```

Input and output are validated with Zod on both sides. A call fails after 30 seconds, and pending
calls are rejected when the plugin stops.

## Troubleshooting

| Symptom | Check |
| ------- | ----- |
| Every plugin shows `disabled` | `pluginsEnabled` is not `true`, or `fde reload` was not run |
| `failed` after install or reload | `fde plugin ls` shows the error; `fde plugin logs <id>` shows compile, load and crash output |
| `Plugin manifest is missing` / `Plugin entry point is missing` | The directory needs `fde-plugin.json` and `index.ts` |
| `Plugin contribution must return a cleanup function` | Return a function from `contribute`, even `() => {}` |
| Sidebar item missing | Wrong host, plugin not `running`, unknown Lucide icon, or `surface` points to an unregistered surface |
| `Module "x" is not available in plugin client code` | Client code imported a module the app does not provide |
| RPC rejected | Input or output failed its schema, the handler threw, or it took over 30 seconds |
| UI did not change after an edit | Run `fde plugin reload <id>` |
| `Plugin ID "x" is already configured` | Pass `--id` or remove the existing plugin |
| CLI reports `DAEMON_UPDATE_REQUIRED` | The host predates plugin management, logs or Git installs; update it |

Logs keep the last 500 lines (256 KiB) per plugin in memory. Reload, disable and crashes keep
them; `remove` and a daemon restart clear them. Copies also go to `$FDE_HOME/daemon.log`, which is
where Git `build` command output is written. Do not log secrets.
